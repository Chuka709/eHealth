# OPS_RUNBOOK.md — нөөцлөлт, сэргээлт (Phase 8.2)

> Хариуцагч: компанийн [үйл ажиллагаа хариуцсан ажилтан]. Энэ баримт кодтой хамт өөрчлөгдөнө
> (`infra/backup/`, `infra/postgres/init/03-backup-role.sh`). Нууцлалын бодлогод бичсэн хугацаа
> (`web/src/legal/content.ts`: «35 хоногийн дотор») энд ба `.env`-д ижил байна.

## 1. Юуг, хэрхэн нөөцлөх вэ
| Хэсэг | Хэрхэн | Шифрлэлт |
|---|---|---|
| Мэдээллийн сан `labtrack` | `pg_dump -Fc`, export хийсэн нэг snapshot-оос | age → нийтийн түлхүүр |
| Role, эрх | `pg_dumpall --globals-only --no-role-passwords` (нууц үг нөөцөд ордоггүй) | age |
| Баримтын файлууд (S3 bucket) | `rclone copy` → tar | апп файл бүрийг шифрэлсэн + age |
| `manifest.json` | migration head, хүснэгт бүрийн мөрийн тоо, FORCE RLS-тэй хүснэгтийн нэрс, policy-ийн тоо, объектын тоо — dump-тай **нэг snapshot**-оос; зөвхөн тоо, хүснэгтийн нэр | шифрлэлтгүй (PHI-гүй) |
| `SHA256SUMS` | бүх файлын hash | — |

- Нөөцийг `labtrack_backup` role хийнэ: `pg_read_all_data` + `BYPASSRLS`, superuser биш, бичих
  эрхгүй. Нууц үг нь compose secret → tmpfs дээрх pgpass (орчны хувьсагчид, `docker inspect`-д харагдахгүй).
- OpenBao snapshot (KEK + хэрэглэгчийн түлхүүр): DB нөөцөөс **тусдаа** газар, хадгалах хугацаа **≤ 35
  хоног** — устгасан аккаунтын түлхүүр snapshot-д үлддэг (SERVER_INSTALL_PLAN §3.7).
- Нөөцлөгддөггүй: Valkey (түр дараалал), ClamAV-ийн гарын үсэг, **KEK (үйлчилгээний мастер
  түлхүүр)**. KEK-гүй бол баримтын файл уншигдахгүй — KEK-ийн нөөцийг age түлхүүр болон нөөцөөс
  **тусдаа** газар (нууцын сан/OpenBao, өөр хүмүүс) хадгална [хаана, хэн — B1-тэй хамт].
- S3: production-д нөөцөд зөвхөн унших эрхтэй тусдаа key ашиглана.

## 2. Түлхүүр (age)
- Нэг удаа, **офлайн машин дээр** (PowerShell-ийн `>` UTF-16 бичдэг тул файлыг контейнер өөрөө бичнэ):
  `docker compose -f infra/docker-compose.yml --profile ops run --rm -T --no-deps -v <хавтас>:/out backup age-keygen -o /out/backup-identity.txt`
- Нийтийн түлхүүр (`age1…`, файлын тайлбар мөрөнд) → `.env`-ийн `BACKUP_AGE_RECIPIENT`. Хувийн
  түлхүүр (`AGE-SECRET-KEY-…`) → компанийн нууц үгийн менежер + цаасан хуулбар сейфэнд;
  **серверт хэзээ ч бүү үлдээ**. Хоёр хүн хандана; жил бүр шалгана.
- Түлхүүр солих: шинэ хос үүсгэж `.env`-д солино; хуучин хувийн түлхүүрийг 35 хоног (хуучин нөөц
  дарагдтал) хадгалаад устгана. Хувийн түлхүүр **задарсан** бол → `BREACH_PROCEDURE.md` (хуучин
  түлхүүрээр шифрлэсэн бүх нөөц задарсанд тооцогдоно).

## 3. Өдөр бүрийн нөөцлөлт
```
just backup
```
- Production-д cron/systemd timer-ээр өдөр бүр [02:00 UB]; сүүлийн мөр `backup ok: …`.
  Мөр ирээгүй, эсвэл exit ≠ 0 бол [хариуцагч]-д дохио (мониторинг — B1).
- Нөөц эхлээд нууц нэрээр (`.<огноо>.partial`) бичигдэж, бүрэн болсны дараа нэрлэгдэнэ;
  pipeline-ийн аль нэг алдаа (pg_dump, rclone, age) бүх нөөцийг зогсооно (`pipefail`).
- Хадгалах хугацаа `BACKUP_RETENTION_DAYS=35` — нэрийн огноогоор тооцно; өдөр бүр ажиллахад
  ямар ч нөөц 35 хоногоос хуучин болохгүй. Устгасан аккаунт 30 хоногийн дараа системээс,
  дараагийн 35 хоногт нөөцөөс алга болно.
- **Гадагш хуулбар (off-site):** `./backups/<огноо>/`-г өөр байршилд өдөр бүр хуулна:
  тусдаа credential (зөвхөн нэмэх эрх), object lock / immutability (ransomware эсрэг), lifecycle
  яг **35 хоног**. Шифрлэгдсэн тул хадгалагч уншиж чадахгүй. Байршлын улс/харьяаллыг хуульчтай
  (Q12). [Байршил — компани, B1.]
- **Логийн хадгалалт ≥ 35 хоног, өөр газарт:** `account_deletion_requested` (зөвхөн user_id) мөрүүд
  §5.6-д хэрэгтэй.

## 4. Сэргээх сургуулилт (сар бүр + release бүрийн өмнө)
```
just restore-drill <хувийн түлхүүрийн файл> [<нөөцийн нэр>]
```
- **Тусдаа контейнерт, сүлжээгүй**, tmpfs дээрх түр Postgres-д сэргээнэ — live cluster-т огт
  хүрэхгүй (эвдэрсэн/хуурамч dump superuser-ээр ажиллаж серверт хүрэх эрсдэлгүй). Нөөц read-only.
- Шалгадаг зүйл: hash → globals-оос role-ууд үүсэх → `pg_restore --exit-on-error` → migration
  head, хүснэгт бүрийн мөрийн тоо, FORCE RLS-тэй хүснэгтийн жагсаалт, policy-ийн тоо manifest-тэй
  **яг тэнцүү** → архивын объектын тоо (задлахгүйгээр тоолно).
- Тайлсан юу ч дискэнд бичигдэхгүй (tmpfs); тасарвал контейнертэй хамт алга болно.
- Түлхүүрийн файлыг сургуулилтын дараа машинаас устгана. Том сан бол `DRILL_TMPFS_SIZE`-ийг өсгөнө (анхдагч 2g).

## 5. Жинхэнэ сэргээлт (гамшиг)
1. Зарлах: [хариуцагч] шийднэ; хэрэглэгчдэд «засвартай» мэдэгдэл; зөрчил байж болзошгүй бол
   `BREACH_PROCEDURE.md`.
2. Эхлээд сонгосон нөөцийг `just restore-drill`-ээр шалгана.
3. Шинэ сервер: нууцуудыг нууцын сангаас (DB role-ийн нууц үг, KEK, S3, JWT). Postgres-ийг
   хоосон эхлүүлнэ — role-уудыг **init скриптүүд ба `just db-roles`** үүсгэнэ; нөөцийн
   `globals.sql`-ийг **ажиллуулахгүй** (зөвхөн харьцуулж шалгана). Superuser зөвхөн
   `createdb labtrack owner labtrack_owner` ба шаардлагатай extension-д. Сэргээлтийг
   **`labtrack_owner`-оор**: `pg_restore --no-owner --exit-on-error -U labtrack_owner -d labtrack`
   (объект бүр owner-ынх, grant-ыг owner өөрөө тавина; хуурамч `ALTER ROLE … SUPERUSER`,
   `COPY … PROGRAM` superuser-гүйгээр ажиллахгүй). Нөөцийг **object lock-той off-site хуулбараас**
   авна.
4. Файлууд: `files.tar.age` тайлж bucket руу `rclone copy`.
5. `just migrate` (head таарах ёстой), API/worker асаана; мөрийн тоо, head-ийг гараар тулгана.
6. **Нөөцөөс хойш устгуулсан аккаунтуудыг дахин устгах** — §5-ын алхам 5-ын migrate-ийн дараа,
   **API-г хэрэглэгчдэд нээхээс, maintenance worker/beat-ийг (устгалт) асаахаас өмнө** (хооронд нь
   хэрэглэгч нэвтэрч, эсвэл цуцлагдсан аккаунт устаж болохгүй):
   1. Нөөцийн цаг (manifest-ийн нэр, UTC) ба API-ийн логийг тэр цагаас хойш бүтнээр нь файлд
      (лог хадгалах газраас экспорт эсвэл `docker compose logs api --no-log-prefix`).
   2. Dry run: `just redelete <нөөцийн цаг, жишээ 2026-11-18T06:17:35Z> <логийн файл>` —
      аккаунт бүрийн сүүлийн үйл явдал (`account_deletion_requested` / `account_deletion_cancelled`)
      ба үр дүн: `would_reapply`, `already_pending`, `absent` (нөөцөөс хойш үүссэн эсвэл аль хэдийн
      устгагдсан — хийх зүйлгүй), `not_eligible` (админ), `cancelled`.
   3. `just redelete <цаг> <файл> --apply` — нэг transaction-д: `deleted_at`-ийг **хүсэлтийн
      анхны цагаар** (30 хоногийн устгалт хугацаагаа хадгална; 30-аас хэтэрсэн бол дараагийн
      өдрийн maintenance устгана), сесс, идэвхжүүлэх токен цуцална, аудит
      `account.deletion_reapplied` (actor `cli`). Дахин ажиллуулахад `already_pending`.
   4. `cancelled_but_pending` (exit 3) — нөөцийн өмнө хүсэж, нөөцийн дараа админ цуцалсан: сэргээсэн
      мөр устгалт хүлээсэн хэвээр. Автоматаар буцаахгүй (лог commit-ээс өмнө бичигддэг тул цуцлалт
      бодитоор хийгдсэн эсэх тодорхойгүй): админы бүртгэлтэй тулгаж admin web-ээр дахин цуцална —
      **үүний дараа л** maintenance-ийг асаана. `cancelled` — хүлээгдэж буй устгал байхгүй, хийх зүйлгүй.
   Лог задлагч зөвхөн бүтэн мөр, өөрийн logger-ийн (`labtrack.api.me` хүсэлт, `labtrack.api.admin`
   цуцлалт) `info` мөрийг, нөөцийн цагаас одоо хүртэлхийг тооцно; эвдэрсэн JSON мөрийг алгасна.
   Гаралт зөвхөн ID ба тоо (дүрэм 3). Тест: `tests/unit/test_redelete_logs.py`,
   `tests/rls/test_redelete.py`.
7. Алдагдсан хугацаа (RPO ≤ 24 цаг): хэрэглэгчдэд «[огноо]-ноос хойш оруулсан мэдээллээ шалгана
   уу» гэж мэдэгдэнэ; утасны офлайн дараалал хэсэгчлэн нөхнө.
8. Зөрчлийн улмаас сэргээсэн бол бүх сессийг цуцална (JWT түлхүүр солих).

## 6. Хязгаар
- **API-ийн лог ≥ 35 хоног хадгалагдана** (хамгийн хуучин нөөцийн хугацаанаас урт) — үгүй бол §5.6
  нөөцөөс хойшхи устгах хүсэлтийг сэргээж чадахгүй (компани, B1 лог хадгалалт).
- RPO 24 цаг (өдөр бүрийн dump). Илүү богино хэрэгтэй бол WAL архив/PITR — 8.3-ийн ачааллын тестийн дараа.
- Устгасан хэрэглэгчийн мэдээлэл нөөцөд 35 хоног хүртэл үлддэг (шийдвэр 2026.11.18: нөөцийн
  хугацаагаар; файлын түлхүүрийг хэрэглэгчийн түлхүүрээр боох нь OpenBao-той хамт дараа).
- `SHA256SUMS` гарын үсэггүй: нөөцийн хавтас руу бичих эрхтэй хүн хуурамч нөөц үүсгэж болно —
  сургуулилт тусгаарлагдсан тул live серверт хүрэхгүй; жинхэнэ сэргээлтийн өмнө §5.2 заавал.
  Off-site хуулбарын object lock нь өөрчлөлтөөс хамгаална.
